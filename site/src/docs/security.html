Natter can see and change everything a Context's credentials allow, so it is built to keep that power on your machine and in your hands.

Your browser never talks to NATS

Natter's own server talks to NATS. Your browser talks only to Natter, over a small API and one live connection. Credentials never reach the browser.

Localhost only

Natter listens on 127.0.0.1 by default. Every request must name an allowed host, and anything that changes state, and the live connection, must come from Natter's own origin. That stops other websites, and DNS-rebinding tricks, from driving it through your browser. To listen on another address you have to say so with -bind and list the hostnames with -allowed-host.

The Launch token

Each run of Natter makes a random Launch token. A browser presents it once, in the sign-in URL, and gets a session cookie (HTTP-only, same-site strict). Without it, a browser gets nothing.

  • The desktop app hands it straight to its own window and never prints it.
  • natter prints the sign-in URL in your terminal.
  • natter open hands it straight to a browser app window and never prints it.
  • On a shared machine, other users can see a browser's command line (not the desktop app's). natter open -redirect-file passes a file only you can read instead.

Read-only mode

Lock any Context and Natter's server refuses every change and every send while it is active, requests included. See Read-only mode.

Browsing changes nothing

Looking at messages uses no durable consumers, sends no acks and moves no consumer's position. The only trace is the short-lived consumer it creates and deletes, which is labelled Natter browsing. On work-queue and interest streams Natter uses Direct Get instead, because there even a reader could change what is kept.

No plaintext secrets

  • Natter never writes a secret in plain text. It stores secrets in the encrypted Vault, or as references to environment variables, 1Password or nsc.
  • It flags natscli contexts that hold plaintext secrets, and moves them into the Vault for you.
  • The OS keyring holds only the Vault key, never the secrets.

Payloads are only ever text

Message payloads are shown as text, a JSON tree or hex, never rendered as a web page, and downloads are served so a browser can't run them. A malicious message can't run code in Natter.
