The Message browser scrolls through a stream's messages, from a handful to hundreds of thousands, and opens any one of them. Looking changes nothing.

Pick a stream

Choose the stream in the page header. The choice is part of the address (/messages?stream=ORDERS), so you can reload or bookmark it. A stream's own Messages tab shows the same browser.

The table

Each row is one message: its sequence, when the server received it (UTC), subject, size, number of headers, and a preview of small payloads. Large and binary payloads say so instead: they load only when you open the message. Gaps in the sequence (deleted messages) are simply skipped.

Scroll freely. Rows load in pages of 100 as you go, and at most 5,000 rows of metadata are kept in memory. On very long streams the scrollbar is scaled to fit, while the mouse wheel and keys still move row by row. The footer says which rows you're seeing.

Filter and jump

  • Subject filter: type a subject, with * and > wildcards, and press Enter. The count updates to the matching messages.
  • Jump to seq: type a sequence number and press Enter.
  • Jump to time…: pick a date and time (UTC) to start from the first message after it.

Open a message

Click a row. The message opens in a panel with its subject, stream, sequence, time and size, then its headers and payload.

  • Step to the previous or next message with ↑ / ↓ (or k / j), across pages and gaps. Esc closes it.
  • View the payload as Text, JSON (a folding tree) or Hex. A large payload shows its first 64 KB; choose Load full for the rest, or Download it.
  • Save as example keeps it as an Example message in the folder "from messages", ready to send again. This works for text payloads up to 512 KiB.
  • Delete… removes it from the stream, optionally overwriting its data on disk (Erase). Blocked in Read-only mode.

No side effects

Natter reads messages through one short-lived, ordered consumer per open table. It acks nothing, moves no other consumer, and is deleted when you leave. It shows up on the Consumers screen labelled Natter browsing while it exists.

Work-queue and interest streams

On these streams even a browsing consumer could change what is kept, so Natter lists their messages with Direct Get instead. That transfers every listed payload, so large messages load more slowly. The table says when this happens.
