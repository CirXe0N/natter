# Build nats-ui's backend on jsm.go, not natscli

ADR-0001's bet holds: nearly every building block nats-ui needs already exists as an importable, Apache-2.0 Go library, but the library is **jsm.go plus nats.go, not natscli**. natscli is the reference implementation to copy patterns from. Its reusable logic sits in `internal/` packages that Go refuses to import, and its public `cli` package is a command tree, not an API. The pieces line up like this. jsm.go v0.5.1's rewritten `natscontext` loads and saves Contexts exactly as natscli does, and it accepts a custom resolver for Vault references. jsm.go's `Manager` and `serverdata` cover stream administration and `$SYS` requests. nats.go v1.55.0's `jetstream` package covers KV, Object Store and the headers-only ordered consumer that Browsing needs. On the web side, the standard library (Go 1.26+) and `coder/websocket` cover routing, CSRF and WebSockets. `zalando/go-keyring` and `filippo.io/age` build with no cgo on every release target. Most of the research confirms the three ADRs, but it changes how several of them get implemented. Browsing must use **one ordered consumer per open view, not one per page**. The keyring should hold **one Vault key, not every secret**. **WorkQueue streams cannot be browsed with a consumer at all**. And a working `go install` requires **committing the built frontend**. A handful of decisions are left for you, collected in the final table.

## natscli is the reference; jsm.go and nats.go are the libraries

The bigger finding for ADR-0001 is how much of natscli's behaviour sits in jsm.go, where it can be imported. In v0.5.x, `natscontext` was rebuilt around a `Registry` that combines a storage `Backend`, a `Selector` for the active Context, and a map of `CredentialResolver`s keyed by URI scheme ([BACKENDS.md](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/BACKENDS.md#L5-L14)). **natscli builds its Registry from `NewDefaultFileBackend()`, `WithDefaultResolvers()` and `WithLocalSelector()`** ([cli/util.go L519-L591](https://github.com/nats-io/natscli/blob/v0.5.1/cli/util.go#L519-L591)), so nats-ui can build the same thing. It would use `NewFileBackendAt(appDir)` for its own directory and a resolver for its Vault scheme. `Context.NATSOptions()` then turns a loaded Context into `[]nats.Option`, applying auth in natscli's exact precedence: user/password, then creds, then nkey, then JWT+seed ([context.go L405-L510](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/context.go#L405-L510)). Showing the CLI's Contexts next to the app's own takes a second Registry over `~/.config/nats` with `WithoutSelection()`. That way nats-ui never touches natscli's `context.txt`, which satisfies ADR-0002's "never edits CLI files without asking". Three traps come with this API. Passing any resolver option drops the defaults, so `WithDefaultResolvers()` must be repeated alongside the custom one ([credentials.go L40-L54](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/credentials.go#L40-L54)). `WithEmbedding`/`SaveEmbedded` write `data:;base64,` creds, which ADR-0002 forbids ([credentials.go L70-L91](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/credentials.go#L70-L91)). And `NewFileBackendAt(dir)` **always appends `nats/context/`**, so the app's directory layout follows from that ([backend_file.go L46-L93](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/backend_file.go#L46-L93)).

For the NATS operations, the answer is to **split the work between jsm.go and nats.go as natscli does**. natscli's stream and consumer commands use jsm.go and its KV, object and subscribe commands use nats.go `jetstream`, all on one shared `*nats.Conn` ([cli/util.go L406-L515](https://github.com/nats-io/natscli/blob/v0.5.1/cli/util.go#L406-L515)). The jsm.go side covers stream and consumer CRUD, purge with a count (`PurgeExt`), message delete with an erase choice, `StreamContainedSubjects`, and batch Direct Get with `MaxBytes` and `StartTime` ([streams.go L810-L1052](https://github.com/nats-io/jsm.go/blob/v0.5.1/streams.go#L810-L1052)). nats.go provides KV, Object Store and ordered consumers. jsm.go has no KV or Object Store client, and nats.go has no batch Direct Get ([stream.go L565-L595](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/stream.go#L260-L595)). The two libraries make different stability promises. nats.go follows Go's compatibility guidelines ([README](https://github.com/nats-io/nats.go/blob/v1.55.0/README.md#L375-L386)). jsm.go is pre-1.0, broke its API in v0.5.0, and describes itself as tooling that "requires deep technical knowledge of the JetStream internals" ([jsm.go README](https://github.com/nats-io/jsm.go/blob/v0.5.1/README.md); [v0.5.0](https://github.com/nats-io/jsm.go/releases/tag/v0.5.0)). Pin jsm.go exactly, keep it behind nats-ui's domain layer, and set floors of **jsm.go ≥ v0.5.1** (direct-batch correctness fix) and **nats.go ≥ v1.55.0** (ordered-consumer `Fetch`/`FetchNoWait` fixes on the browsing path) ([jsm.go v0.5.1](https://github.com/nats-io/jsm.go/releases/tag/v0.5.1); [nats.go v1.55.0](https://github.com/nats-io/nats.go/releases/tag/v1.55.0)).

The System credentials features also come from jsm.go. Its `serverdata` package powers `nats server request/report`. It provides scatter-gather `DoReq` with expected-reply counting and typed `Varz`, `Connz`, `Jsz`, `Healthz` and `Statz` calls, all returning nats-server's own types ([serverdata/live.go](https://github.com/nats-io/jsm.go/blob/v0.5.1/serverdata/live.go#L13-L78)). KICK and RELOAD are single `DoReq` calls to `$SYS.REQ.SERVER.<id>.KICK|RELOAD` ([server_request_command.go L291-L297](https://github.com/nats-io/natscli/blob/v0.5.1/cli/server_request_command.go#L291-L297)). Pass `api.NewDiscardLogger()` rather than nil, because `DoReqAsync` logs unconditionally ([request.go](https://github.com/nats-io/jsm.go/blob/v0.5.1/serverdata/request.go#L26-L50)). Importing nats-server for those types costs nothing extra, because **jsm.go's root package already imports `nats-server/v2/server`** ([manager.go L29](https://github.com/nats-io/jsm.go/blob/v0.5.1/manager.go#L29)). The same `server.Varz`/`server.Connz` structs also decode the HTTP monitoring JSON, so the Monitoring URL fallback can share one decoder. The lighter orbit `natssysclient` avoids nats-server but has no KICK or RELOAD ([natssysclient](https://github.com/synadia-io/orbit.go/tree/52b976df6160cace6c81a5c5f43b1284dbabbf93/natssysclient)).

The one piece that must be copied is natscli's templating, which the glossary's **Placeholder** depends on. `PubReplyBodyTemplate` lives in `natscli/internal/util` ([headers.go L68-L120](https://github.com/nats-io/natscli/blob/v0.5.1/internal/util/headers.go#L68-L122)), and Go's internal-package rule blocks the import ([Go 1.4 notes](https://go.dev/doc/go1.4#internalpackages)). The function is about 40 lines and Apache-2.0, so vendor it with its copyright header and a golden test. Copying it exactly brings four behaviours the glossary doesn't mention. Each placeholder is evaluated separately, so `{{ID}}` in the body and in a header yields two different NUIDs. Header *names* are never templated. A bad template leaves the text unchanged instead of failing. And **natscli templates header values even with `--templates=false`** ([headers.go L50-L66](https://github.com/nats-io/natscli/blob/v0.5.1/internal/util/headers.go#L50-L66); [pub_command.go](https://github.com/nats-io/natscli/blob/v0.5.1/cli/pub_command.go#L70-L113)). The app can drop that last quirk, but it should say so. All five NATS repositories are Apache-2.0 with no NOTICE file ([natscli LICENSE](https://github.com/nats-io/natscli/blob/v0.5.1/LICENSE)), so the release only needs a bundled third-party licences file.

## Three server-side layers stop rebinding, CSRF and socket hijacking

ADR-0001's security model is right, and the standard library now does most of the work. Each layer stops a different attack, and only one of them stops DNS rebinding. On a rebound domain the attacker's page is same-origin with itself (`evil.example:PORT`), so Origin equals Host and Origin checks pass. **Only a strict Host allow-list stops it**, which is why Jupyter blocks non-loopback Hosts unless `allow_remote_access` is set ([jupyter_server handlers.py](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/base/handlers.py)). It is also why Vite's CVE-2025-24010 fix added `server.allowedHosts` and a WebSocket Origin check ([GHSA-vg6x-rcgg-rjx6](https://github.com/vitejs/vite/security/advisories/GHSA-vg6x-rcgg-rjx6)). For cross-site requests, Go 1.25's `http.CrossOriginProtection` rejects unsafe cross-origin requests using `Sec-Fetch-Site`, falling back to an Origin-vs-Host comparison ([pkg.go.dev](https://pkg.go.dev/net/http#CrossOriginProtection); [Valsorda](https://words.filippo.io/csrf/)). It deliberately allows GET, HEAD and OPTIONS, so **the domain API must never change state on GET**. The WebSocket upgrade is also a GET, so it needs its own Origin check. `coder/websocket` provides that by default: `Accept` rejects cross-origin handshakes unless `OriginPatterns` allows them ([pkg.go.dev coder/websocket](https://pkg.go.dev/github.com/coder/websocket)).

These defaults refine ADR-0001's wording in two places. First, "every request needs … an expected Origin" is stricter than what the standard library does. Go allows requests that carry neither `Sec-Fetch-Site` nor Origin, while OWASP says missing headers "are not evidence of a same-origin request" ([OWASP CSRF cheat sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). The session cookie covers that gap: curl and scripts still need a session obtained with the token. Origin is checked on unsafe methods and on the upgrade, and `Origin: null` is rejected. Second, cookies **do not isolate by port** ([RFC 6265 §8.5](https://www.rfc-editor.org/rfc/rfc6265#section-8.5)). The session cookie should therefore be HttpOnly, `SameSite=Strict`, `Path=/`, carry a port-specific name such as `natsui_session_<port>`, and hold an opaque per-process ID. `__Host-` and `Secure` require TLS, so they apply only to a TLS non-loopback bind. Sessions and tokens should use `crypto/rand.Text()`, which gives at least 128 bits in URL-safe base32 ([crypto/rand](https://pkg.go.dev/crypto/rand#Text)), compared with `subtle.ConstantTimeCompare`. For a non-loopback bind, the Host allow-list cannot simply be switched off. It needs an explicit `--allowed-host` list, following Jupyter's `local_hostnames` and Vite's "always using an explicit list" advice ([Vite server options](https://vite.dev/config/server-options)).

The glossary says a browser presents the Launch token "once". That leaves the token's lifetime open. A strictly single-use token breaks second browsers, private windows and cleared cookies, and the auto-opened browser can consume the token before the user's preferred one does. Jupyter keeps its token for the server's lifetime ([Jupyter security docs](https://jupyter-server.readthedocs.io/en/latest/operators/security.html)). The workable design is the same: the token stays valid until the process exits, each exchange at `/launch?token=` mints a fresh in-memory session, and the response redirects with 303 and `Referrer-Policy: no-referrer` so the token leaves the address bar. Opening the browser via `github.com/cli/browser`, the maintained fork, puts the token in the opener's argv for a moment. Jupyter's `use_redirect_file` exists to avoid exactly that on shared machines ([serverapp.py](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/serverapp.py)), and nats-ui could offer the same as an option.

Serving and routing are straightforward. `//go:embed all:dist` with `fs.Sub` serves the Vite build ([pkg.go.dev/embed](https://pkg.go.dev/embed)). A small wrapper gives hashed `assets/*` an immutable cache header, serves `index.html` with `no-cache` for client-side routes, and returns a **real 404 for missing assets**, so a stale tab does not get HTML where it expected a JS chunk. The Go 1.22 ServeMux patterns (`GET /api/streams/{name}`) and four plain middlewares (Host, session, cross-origin, Read-only) cover the API, so chi is optional ([routing enhancements](https://go.dev/blog/routing-enhancements)). Go 1.27.3 is current and Go 1.25 is out of support, so set `go 1.26` or later ([release history](https://go.dev/doc/devel/release)). On 1.27, `encoding/json` runs on the v2 implementation and error strings change ([Go 1.27](https://go.dev/doc/go1.27)). Live data should travel over **one multiplexed WebSocket per tab**, not SSE. Over plain HTTP/1.1 on loopback, SSE is capped at six connections per browser and can't carry subscribe messages ([MDN SSE](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)). Use `coder/websocket` (v1.8.15, active) rather than gorilla/websocket, which has had no release since June 2024 ([GitHub coder/websocket](https://github.com/coder/websocket); [gorilla](https://pkg.go.dev/github.com/gorilla/websocket)). In development, Vite on :5173 proxies `/api` and `/ws` to Go. That makes Origin differ from Host, so a `--dev` flag must add `http://localhost:5173` as a trusted origin for both `CrossOriginProtection` and the WebSocket.

## Keep the keyring for one Vault key, not every secret

ADR-0002 picked the right libraries, but `zalando/go-keyring` is more fragile than the ADR assumes. It needs no cgo on Linux, macOS (it shells out to `/usr/bin/security`) or Windows ([README](https://github.com/zalando/go-keyring/blob/master/README.md); [keyring_unix.go](https://github.com/zalando/go-keyring/blob/master/keyring_unix.go)). But it **has no timeout and no availability check**. On Linux, godbus may autolaunch `dbus-launch` and rewrite the process environment ([godbus conn.go](https://github.com/godbus/dbus/blob/v5.2.2/conn.go)). A locked collection blocks forever in `handlePrompt` ([secret_service.go](https://github.com/zalando/go-keyring/blob/master/secret_service/secret_service.go)). Open issues report hangs on headless machines, in containers, on WSL and with KeePassXC ([#118](https://github.com/zalando/go-keyring/issues/118), [#116](https://github.com/zalando/go-keyring/issues/116), [#88](https://github.com/zalando/go-keyring/issues/88)). GitHub CLI wraps every call in a 60-second timeout ([cli/cli keyring.go](https://github.com/cli/cli/blob/trunk/internal/keyring/keyring.go)), and nats-ui must do the same. It should first probe with `SessionBusPrivateNoAutoStartup` for an owned or activatable `org.freedesktop.secrets`, then do a canary set/get/delete under a short deadline. If that fails, it falls back to the age file. Values are capped at **2,560 bytes on Windows and about 3,000 bytes on macOS** ([keyring.go](https://github.com/zalando/go-keyring/blob/master/keyring.go); [CREDENTIALW](https://learn.microsoft.com/en-us/windows/win32/api/wincred/ns-wincred-credentialw)). `ListUsers` is merged but not in any tag ([PR #135](https://github.com/zalando/go-keyring/pull/135)). Item names must avoid `\` and `'` because of a macOS bug ([#154](https://github.com/zalando/go-keyring/issues/154)).

Those limits point to one design: **always store secrets in `vault.age`, and use the keyring only to hold the age identity that decrypts it.** That gives one code path and one file format for every backend. It sidesteps the size caps that `.creds` files can approach, needs no `ListUsers`, and costs one KeePassXC confirmation instead of one per secret. Switching backend then only re-wraps the key. The cost is that a ciphertext file exists even on desktops with a keyring. That contradicts the literal text of ADR-0002 ("The Vault is the OS keyring") and the glossary's **Vault** definition, so you need to decide on it.

The age side of ADR-0002 needs a similar adjustment, because **an scrypt (passphrase) recipient must be the only recipient of a file** ([scrypt.go](https://github.com/FiloSottile/age/blob/v1.3.2/scrypt.go); [C2SP age spec](https://github.com/C2SP/C2SP/blob/main/age.md)). To support both a key file and a typed passphrase, nats-ui should encrypt `vault.age` to an identity. The "key file passed on the command line" is then a plaintext age identity file. Passphrase mode keeps a scrypt-wrapped copy of that identity in `vault.key.age`, which is the age CLI's own passphrase-protected key pattern ([age README](https://github.com/FiloSottile/age/blob/v1.3.2/README.md)). Changing the passphrase then rewrites only the small wrapper. New vaults should default to a hybrid post-quantum identity (`GenerateHybridIdentity`), which age v1.3 calls "the standard age public key" ([pq.go](https://github.com/FiloSottile/age/blob/v1.3.2/pq.go)). Plugins and SSH keys are out of scope for v1: plugins run external binaries and need an interactive `ClientUI`. Writes reuse natscontext's pattern: temp file at 0600, fsync, rename, fsync the directory ([backend_file.go](https://github.com/nats-io/jsm.go/blob/main/natscontext/backend_file.go)). A lock file is needed because rename "is not an atomic operation" on non-Unix platforms ([pkg.go.dev/os](https://pkg.go.dev/os)). For memory, memguard buys little when secrets must become Go `string`s for `nats.UserInfo` anyway. A `Secret` type that redacts itself in `fmt`, `slog` and JSON, plus wiping `[]byte` buffers, gives most of the benefit. `runtime/secret` is still experimental and Linux-only ([runtime/secret](https://pkg.go.dev/runtime/secret)).

The natscontext integration adds three constraints. **`NATSOptions` resolves secrets with `context.Background()`** and resolves non-file secrets eagerly, so the Vault must be unlocked before connecting. The resolver must also fail fast with a typed `ErrLocked` instead of blocking ([context.go L406](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/context.go#L406)). The ADR's claim that natscli "passes unknown schemes through as the literal secret" is true only for password, token, JWT and seed. For `creds` and `nkey`, natscli fails with "no resolver registered for scheme" ([credentials.go L156-L176](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/credentials.go#L156-L176)). Either way the separate-directory rule still stands. The serious gap is TLS. **natscontext accepts `cert`, `key` and `ca` only as file paths** "until nats.go exposes in-memory TLS equivalents" ([BACKENDS.md](https://github.com/nats-io/jsm.go/blob/v0.5.1/natscontext/BACKENDS.md#L287-L298)). The glossary counts a TLS key file referenced by path as a **Plaintext secret**. So a Vault-held TLS client key means bypassing `NATSOptions` for TLS and building `nats.Secure(&tls.Config{…})` directly. On naming, the ADR's example scheme `keyring://` is better replaced by a distinctive `nats-ui-vault://<opaque-id>`, which will not collide with a future natscli scheme and is obviously a reference if it ever leaks. The NATS tools use XDG paths on every OS, nsc included ([nsc home.go](https://github.com/nats-io/nsc/blob/main/home/home.go)), so `~/.config/nats/nats-ui/` (or `~/.config/nats-ui/`) keeps nats-ui next to the CLI, unlike `os.UserConfigDir`'s per-OS paths.

## One ordered consumer per view, not per page

ADR-0003's metadata-first design is confirmed at the server level. `headers_only` makes `convertToHeadersOnly` drop the payload and add `Nats-Msg-Size` ([consumer.go L5774-L5790](https://github.com/nats-io/nats-server/blob/v2.15.2/server/consumer.go#L5774-L5790)). nats.go's `OrderedConsumer` creates exactly the consumer Browsing needs: AckNone, R1, in memory, recreated on gaps ([ordered.go L583-L640](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/ordered.go#L583-L640)). The catch is in how it is driven. **Every ordered `Fetch()` calls `reset()`, deleting and recreating the server consumer.** nats.go's own doc tells callers to use `Consume` or `Messages` instead ([ordered.go L419-L478](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/ordered.go#L419-L478)). In a cluster, every consumer create is a meta-leader Raft proposal ([jetstream_api.go L5204](https://github.com/nats-io/nats-server/blob/v2.15.2/server/jetstream_api.go#L5204)). So a page-of-100 `Fetch` loop, which one of the research notes sketched, would cost two meta proposals per scroll step. The right model is one ordered consumer per open table view, read with `Messages()`/`Next()` until 100 rows arrive or `NumPending` reaches zero. A new consumer is created only when the user jumps to a sequence or time or changes the filter. Sequence and timestamp come from `msg.Metadata()` ([message.go](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/message.go#L91-L115)), and `NumPending` drives the approximate scrollbar. `Stop()` does not delete the consumer, so closing a view must call `DeleteConsumer` explicitly. `InactiveThreshold` should be about 30 s rather than nats.go's 5-minute default, clamped to the stream's `ConsumerLimits` or the create is rejected ([consumer.go L690-L695](https://github.com/nats-io/nats-server/blob/v2.15.2/server/consumer.go#L690-L695)). Avoid jsm.go's `StreamPager`: it creates a **durable** consumer with a one-hour threshold ([stream_pager.go](https://github.com/nats-io/jsm.go/blob/74725fff877cf26c1b57591e3d1b2b39b424c037/stream_pager.go#L259-L290)).

Two findings challenge the glossary's **Browsing** definition. First, "leaves no trace" holds for data and consumer positions, but **every create and delete emits a `$JS.EVENT.ADVISORY.CONSUMER.*` advisory** and shows up in `nats consumer ls` ([consumer.go L2025](https://github.com/nats-io/nats-server/blob/v2.15.2/server/consumer.go#L2025)). Consumers should carry a `nats_ui_` prefix and metadata, and the glossary should say that the trace is transient. That also bears on **Read-only mode**, which "blocks every action that changes server state": browsing creates and deletes server objects, so Read-only mode needs an explicit exception for it. Second, **WorkQueue streams reject AckNone pull consumers outright** ([consumer.go L836-L839](https://github.com/nats-io/nats-server/blob/v2.15.2/server/consumer.go#L836-L839)), and consuming with acks would delete messages. On those streams the table can only be built from Direct Get batches, the path ADR-0003 rejected for listing because it transfers payloads. jsm.go's pager uses the same fallback ([stream_pager.go](https://github.com/nats-io/jsm.go/blob/v0.5.1/stream_pager.go#L76-L182)). Interest-retention streams are still untested: no note confirmed whether an extra AckNone consumer changes their retention.

Opening a message uses Direct Get as the ADR says, with one consistency caveat. With `allow_direct`, every peer answers from its local store, and **followers join once they are only 90 % caught up** ([jetstream_cluster.go L4800-L4825](https://github.com/nats-io/nats-server/blob/v2.15.2/server/jetstream_cluster.go#L4800-L4825); [ADR-31](https://github.com/nats-io/nats-architecture-and-design/blob/dc0b1c7200f0d716fdee9de1428759594538ed7d/adr/ADR-31.md#L20-L36)). A message published a moment ago can therefore 404, so on a 404 the backend should retry once via leader-only `STREAM.MSG.GET`. nats.go's `GetMsg` switches between the two automatically based on cached `AllowDirect` ([stream.go L549-L600](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/stream.go#L549-L600)). A payload always arrives as one NATS message, so "render progressively" means slicing a single buffer. The cleanest fit for ADR-0003's "first 64 KB, then load full or download" is an **HTTP payload endpoint using `http.ServeContent` over a `bytes.Reader`**. That gives Range requests for the 64 KB preview, `Content-Disposition` downloads, and no base64 inflation ([net/http ServeContent](https://pkg.go.dev/net/http#ServeContent)), leaving the WebSocket to carry metadata only. The real limit comes from `nc.MaxPayload()`. The server default is 1 MB and it warns above 8 MB ([const.go L92-L99](https://github.com/nats-io/nats-server/blob/v2.15.2/server/const.go#L92-L99)).

The Live tail design agreed on 2026-10-31 maps directly onto nats.go. Use a callback subscription, because `ChanSubscribe` fixes its limit to `cap(ch)` ([nats.go L5972-L5988](https://github.com/nats-io/nats.go/blob/v1.55.0/nats.go#L5972-L5988)). Set modest `SetPendingLimits` so nats.go drops instead of blocking, and read `sub.Dropped()` deltas as natscli `sub` does ([sub_command.go L128-L142](https://github.com/nats-io/natscli/blob/v0.5.1/cli/sub_command.go#L128-L142)). Apply a token-bucket rate cap in the callback. Keep a slice-indexed ring of rows with a byte budget that clears payloads oldest-first and marks those rows as no longer held, which is the "fewer payloads, never fewer messages" rule. The glossary says the tail "reports how many messages it dropped", but there are **three drop sources**: client pending-limit drops, rate-cap drops, and server-side slow-consumer disconnects. The last has no reliable count; `Dropped()` itself "may not be valid" once the server declares a slow consumer ([nats.go L6004-L6019](https://github.com/nats-io/nats.go/blob/v1.55.0/nats.go#L6004-L6019)). Tails should run on a **dedicated `*nats.Conn`**, so a flooded tail cannot stall Browsing. Fan-out to tabs needs per-client bounded queues that suit each feed. Tails drop the oldest frames and send a gap marker. Metrics and KV state collapse to the latest value per key. A client whose write deadline expires gets disconnected; `coder/websocket` closes the connection itself on a write-context timeout. Producers should be reference-counted with a short grace period so a page reload does not churn consumers.

Two other feeds have specific constraints. **STATSZ broadcasts every 10 s and that interval is not configurable**. It is an unexported package variable, and natscli's help text claiming 30 s is stale ([events.go L99-L107](https://github.com/nats-io/nats-server/blob/v2.15.2/server/events.go#L99-L107)). Charts with 1-second resolution therefore need the backend to poll `$SYS.REQ.SERVER.PING.STATSZ` every second. Replies to a private inbox bypass the broadcast rate limit ([events.go L2239-L2263](https://github.com/nats-io/nats-server/blob/v2.15.2/server/events.go#L2239-L2263)). Rates come from deltas of cumulative counters, and a changed `start` marks a restart. Fixed `float32` rings of 3,600 slots hold an hour per series. KV views use `WatchAll(ctx, MetaOnly())`, which delivers current values, a `nil` "initial load done" sentinel, then live updates with deletes included ([kv.go L346-L352](https://github.com/nats-io/nats.go/blob/v1.55.0/jetstream/kv.go#L346-L352)). It is the KV equivalent of the headers-only table, with values fetched on click.

## A real NATS server in every test, and committed assets for go install

Testing against real NATS is cheap, because nats-ui already links the server package through jsm.go. A test starts one with `server.NewServer(opts)`, `go s.Start()`, `ReadyForConnections` and **`Port: -1`, because `0` means 4222, not random** ([const.go L80-L83](https://github.com/nats-io/nats-server/blob/v2.15.2/server/const.go#L80-L83); [opts.go](https://github.com/nats-io/nats-server/blob/v2.15.2/server/opts.go#L6065-L6077)). A config-string helper passed through `server.ProcessConfigFile` covers JetStream, HTTP monitoring, a WebSocket listener, and SYS and APP accounts in one fixture ([opts.go L968](https://github.com/nats-io/nats-server/blob/v2.15.2/server/opts.go#L968)). Building accounts in Go instead requires an explicit `acc.EnableJetStream`, as NUI's test server does ([nui testserver.go](https://github.com/nats-nui/nui/blob/71d1487c47cc/pkg/testserver/testserver.go#L20-L135)). `ReadyForConnections` does not wait for the JetStream meta leader ([server.go](https://github.com/nats-io/nats-server/blob/v2.15.2/server/server.go#L4088)). R3 tests must therefore poll until a stream can be created, as nats.go's `waitForJSCluster` does ([testservice_helper_test.go](https://github.com/nats-io/nats.go/blob/36314d4086cb/jetstream/test/testservice_helper_test.go)). They should also share one cluster per package, the way natscli pre-assigns cluster ports and runs `-p=1` ([natscli nats_test.go](https://github.com/nats-io/natscli/blob/e62a4c123040/nats/tests/nats_test.go#L270-L330)). Operator/JWT mode for real System credentials needs only `resolver: MEMORY` and preloaded JWTs ([operator.conf](https://github.com/nats-io/nats-server/blob/v2.15.2/test/configs/operator.conf)). nats.go and jsm.go have moved to Synadia's `orbit.go/ntf` fixture service ([ntf README](https://github.com/synadia-io/orbit.go/blob/16d67fa064b8/ntf/README.md)). It is v0.0.x and binds the wildcard address, so it is worth adopting only if leafnodes, super-clusters or fault injection become needed.

End-to-end tests should run a **separate `internal/e2e/cmd/e2eserver` harness, not a test mode in the shipped binary**. The harness starts and seeds the embedded server, starts the real handler on `127.0.0.1:0`, and prints one `E2E READY url=… token=…` line. Playwright 1.57+ `webServer.wait` copies named capture groups into `process.env`, and a setup project trades the token for the cookie and saves `storageState` ([Playwright webServer](https://playwright.dev/docs/test-webserver); [auth](https://playwright.dev/docs/auth)). With a separate harness, the Launch-token, Host and Origin checks stay on during e2e, and the shipped binary has no backdoor. It is unverified whether the captured variables exist when `playwright.config.ts` is evaluated, so read them inside tests. On the frontend, Vitest 5 + jsdom + React Testing Library 16 work on Vite 8, React 19 and TypeScript 7 ([Vitest 5](https://vitest.dev/blog/vitest-5)). TypeScript 7's `types: []` default means test type packages must be listed explicitly, and it ships no JS API yet, so type-aware typescript-eslint needs the TS 6 alias ([TS 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)). jsdom computes no layout, so ADR-0003's virtualised table needs Vitest Browser Mode or Playwright ([Browser Mode](https://vitest.dev/guide/browser/)).

The release is standard GoReleaser v2 OSS ([releases](https://github.com/goreleaser/goreleaser/releases)). `before.hooks` run the npm build, and `CGO_ENABLED=0` covers linux, darwin and windows on amd64 and arm64. Nothing in the stack needs cgo: go-keyring shells out on macOS and uses pure-Go D-Bus and wincred elsewhere ([keyring_darwin.go](https://github.com/zalando/go-keyring/blob/66b55cc0c51c/keyring_darwin.go#L29)). Add checksums, a syft SBOM ([sbom](https://goreleaser.com/customization/sbom/)) and cosign keyless `--bundle` signing ([sign](https://goreleaser.com/customization/sign/)). macOS signing and notarization works from Linux through built-in quill but needs a paid Apple Developer ID. It can ship gated on a secret, as GoReleaser's own config does ([notarize](https://goreleaser.com/customization/notarize/)). Version reporting should combine `-X main.version` ldflags with a `debug.ReadBuildInfo()` fallback, since Go 1.24 stamps VCS versions into `go build` and `go install` binaries ([Go 1.24](https://go.dev/doc/go1.24)). The hard constraint is ADR-0001's `go install` channel. `go install` never runs npm or `go generate` ([cmd/go](https://pkg.go.dev/cmd/go#hdr-Generate_Go_files_by_processing_source)), and module zips contain only committed files. **A working `go install` therefore requires committing `web/dist`**, as PocketBase does ([pocketbase ui/embed.go](https://github.com/pocketbase/pocketbase/blob/7f2773ec234b/ui/embed.go)) and Temporal does through a mirror module ([ui-server](https://github.com/temporalio/ui-server/blob/9ba7e3c8b2c2/README.md)). NUI, the closest NATS GUI, commits only a placeholder, so its `go install` builds have no UI ([nui .gitignore](https://github.com/nats-nui/nui/blob/71d1487c47cc/frontend/.gitignore)). Whatever is chosen, keep a committed file in `dist/` so a fresh clone compiles, because an embed pattern with no match is a build error ([pkg.go.dev/embed](https://pkg.go.dev/embed)).

## Where the ADRs hold, bend or break

| Recorded decision | Verdict | What the research shows |
|---|---|---|
| ADR-0001: Go so the backend can reuse natscli's context loading and jsm.go | **Confirms, with a refinement** | Context loading is in jsm.go `natscontext`, which is fully importable and supports pluggable resolvers. natscli's own code (templating) must be copied, not imported. |
| ADR-0001: single binary via GitHub Releases and `go install` | **Challenges** | `go install` serves a full UI only if the built `dist/` is committed to the module. |
| ADR-0001: localhost, Launch-token cookie, Host + Origin checks | **Confirms, refines** | Host allow-list (rebinding), `CrossOriginProtection` (CSRF, unsafe methods only), coder/websocket Origin default (hijacking). Port-specific cookie name. GET must never mutate. Non-loopback binds need an explicit allowed-host list. |
| ADR-0002: unknown schemes pass through as literal secrets in natscli | **Refines** | True for password, token, JWT and seed. creds and nkey fail with an error instead. The separate-directory rule stands either way. |
| ADR-0002: Vault is the OS keyring via go-keyring | **Challenges** | No timeout, D-Bus autolaunch, unlock hangs, 2.5–3 KB caps. Keep only the age identity in the keyring and all secrets in `vault.age`. |
| ADR-0002: age file unlocked by key file or UI passphrase | **Refines** | scrypt must be the sole recipient, so encrypt to an identity, with the key file as an age identity file and the passphrase wrapping that identity. |
| ADR-0002: no Plaintext secrets | **Exposes a gap** | natscontext takes TLS cert, key and CA as paths only. A Vault-held TLS key requires building `tls.Config` outside `NATSOptions`. |
| ADR-0003: headers-only consumer for rows, Direct Get on open | **Confirms, refines** | One ordered consumer per view via `Messages()`, never `Fetch()` per page. Explicit delete, 30 s threshold. Retry a Direct Get 404 on the leader. Serve payloads over HTTP Range. |
| ADR-0003: Direct Get batches rejected for listing | **Challenged for WorkQueue streams** | WorkQueue streams reject AckNone pull consumers, so Direct Get is the only no-trace listing path there. |
| ADR-0003: Live tail memory budget | **Confirms** | Maps onto `SetPendingLimits`, `Dropped()`, a rate limiter and a byte-budgeted ring on a dedicated connection. |
| Glossary: Browsing leaves no trace | **Refines** | No data, ack or position changes, but consumer create and delete advisories are visible, and creation is a server-state change. |
| Glossary: Placeholder uses natscli names | **Confirms, refines** | Same FuncMap, but each placeholder is evaluated separately, header names are never templated, and failures are soft. |
| Glossary: Live tail reports dropped count | **Refines** | Three drop sources. The server-side slow-consumer count is unknowable. |

## Decisions still open for you

| Decision | Options | Research leaning |
|---|---|---|
| Keyring role | Secret per keyring item (ADR text) vs keyring holds only the Vault identity | Identity only. Needs an ADR-0002 and glossary edit. |

| Launch token lifetime | Process-lifetime vs single-use vs rotate after first use | Process-lifetime token, fresh session per exchange |
| Token exposure on shared machines | Plain `browser.OpenURL` vs optional Jupyter-style redirect file | Offer the redirect file as an option |
| `go install` channel | Commit `dist` on release commits vs placeholder UI vs drop `go install` | Commit on release commits, or amend ADR-0001 |
| Live tail parameters | Rate cap, ring size, byte budget, oversize-message policy | ~1,000/s, 10,000 rows, single oversize payload not held |

## Conclusion

The research moves nats-ui's risk away from where ADR-0001 expected it. Reuse is easy: jsm.go's new resolver-based `natscontext`, `serverdata` and nats.go's ordered consumer leave very little NATS code to write. The risk is in edges the libraries don't advertise. go-keyring can block forever. `Fetch` silently recreates consumers. WorkQueue streams refuse the browsing consumer. natscontext has no in-memory TLS path. `go install` can't see uncommitted assets. The ADR wording did not anticipate any of these, and each is now a known design point rather than a surprise during implementation.

Two of the open decisions change the glossary, not just the code. Moving secrets out of the keyring changes what **Vault** means. Admitting that browsing creates transient server objects changes both **Browsing** and **Read-only mode**. Settle them before writing the backend, because the domain API, the Vault file format and the Read-only middleware all depend on those definitions.
