# Build one web UI, then wrap it lightly

Build nats-ui's production frontend from the prototype's own stack: React 19, Vite 8, Tailwind 4 and TypeScript 7. Rebuild it on **shadcn/ui with its new default Base UI primitives**, **TanStack Router** for typed URL state, and **TanStack Query** for REST. Live data goes through a small hand-written client for the one multiplexed WebSocket. Charts use **uPlot**, and the payload editor uses **CodeMirror 6**. Three pieces have to be custom-built, because no library copes at ADR-0003's scale: a scaled-scroll message table, a virtualised JSON tree and a virtualised hex view. The design system needs one real fix first. The prototype's `faint` text colour is its most-used text colour, and it **measures 3.04:1 on panels, which fails WCAG 2.2 AA**. Raising it to `#7d8595`, and `muted` to `#9ca5b6`, makes every text tier pass on every surface. Tokens should move to a three-layer OKLCH scheme mapped onto shadcn's names. That opens the way to a light theme, a high-contrast variant and live Omarchy theme following: the Go backend watches Omarchy's `colors.toml`, re-checks contrast and pushes the tokens over the existing socket. Should nats-ui ship as a desktop app? Yes, but start with the lightest form. A `nats-ui open` launcher starts the server and opens a Chromium `--app=` window with the Launch token in the URL. Add an Omarchy or XDG `.desktop` entry and a PWA manifest, and you get most of a desktop app without touching ADR-0001's single binary or security model. On your NVIDIA and Hyprland machine this also avoids WebKitGTK's documented blank-window problems. If you later need a tray, native menus and installers, upgrade to **Wails v3, stable since 26 October 2026**, in "shell over loopback" mode behind a `desktop` build tag. Tauri is the fallback. Electron and a Qt WebEngine shell are not worth their cost, and a QML rewrite would be a different product. The research mostly confirms ADR-0003 and the prototype's structure. It refines the glossary's Launch token and Placeholder definitions. It challenges ADR-0001's "single binary only" if a true desktop build is adopted.

## shadcn on Base UI, TanStack Router and TanStack Query form the spine

The component base question has changed since the prototype was started. **shadcn/ui made Base UI its default on 2 July 2026.** The reasons given were that "Base UI is stable", at 1.6.0 with 6M+ weekly downloads, and that new projects "pick Base UI over Radix 2 to 1". Radix is "not being deprecated", and every update ships for both ([shadcn changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-07-base-ui-default.mdx)). React Aria became a third first-class base on 17 July 2026 ([shadcn changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-07-react-aria.mdx)). It has the strongest documented screen-reader and i18n testing, with "translations in over 30 languages" ([react-aria.adobe.com](https://react-aria.adobe.com/)). But its shadcn base is three months old, and its render-prop API is further from the shadcn idiom. Base UI follows the WAI-ARIA Authoring Practices and manages focus. It leaves visible focus styles, colour contrast and accessible names to the app ([Base UI accessibility](https://base-ui.com/react/overview/accessibility)), and section 4 shows those are exactly where the prototype is weak. The recommendation is `npx shadcn@latest init -t vite` on the default Base UI base. Treat the components as code you own, and pull upstream fixes periodically with CLI v4's `--diff` ([CLI v4 changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-03-cli-v4.mdx)). Ark UI has no shadcn base, so choosing it would lose the copy-in registry workflow ([shadcn changelog](https://ui.shadcn.com/docs/changelog)).

Two pieces of shadcn's registry still reach outside Base UI. **The `Command` component wraps cmdk.** cmdk's last release was 1.1.1 on 14 March 2025, and its last commit (29 October 2025) was a README edit ([dip/cmdk commits](https://api.github.com/repos/dip/cmdk/commits)). cmdk also pulls `@radix-ui/react-dialog` and three other Radix packages into a Base UI app ([npm cmdk](https://www.npmjs.com/package/cmdk)). It still works on React 19 and has 44M weekly downloads, so it is finished software, not broken software. The prototype already has the seam that makes this safe: `kit.tsx`'s `CommandPalette` over a `Command[]` from `commands.ts`. Wrap cmdk behind that interface now, and a later move to Base UI's Combobox becomes a one-file change. Second, **shadcn's Sonner wrapper imports `next-themes`**, which a Vite app does not want. The Base UI Toast that shadcn added on 23 July 2026 supports "actions, status types, promises, stacking, and swipe dismissal" ([shadcn toast changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-07-toast.mdx)), and it keeps the app on one set of primitives. Use `react-resizable-panels` 4.15.3, which is actively maintained with one open issue ([npm](https://www.npmjs.com/package/react-resizable-panels)), for the table-and-drawer and editor-and-result splits. Leave out `vaul` (last release December 2024) and `tailwindcss-animate` (August 2023). shadcn itself now imports `tw-animate-css` ([shadcn eject changelog](https://github.com/shadcn-ui/ui/blob/main/apps/v4/content/docs/changelog/2026-05-shadcn-eject.mdx)). Hotkeys can stay hand-rolled, because `@tanstack/react-hotkeys` is still 0.19 ([npm](https://www.npmjs.com/package/@tanstack/react-hotkeys)).

**For routing, use TanStack Router (1.170.x).** Its `validateSearch` takes a Zod v4 schema directly. With `.catch()` fallbacks, a malformed share-link degrades to defaults instead of an error page. `stripSearchParams` keeps links short by dropping values that equal their defaults ([TanStack Router search params](https://tanstack.com/router/latest/docs/framework/react/guide/search-params)). React Router is now v8, released 17 June 2026, and its type-safe route API is Framework mode only ([React Router modes](https://reactrouter.com/start/modes); [changelog](https://reactrouter.com/changelog)). An embedded SPA would have to hand-roll parse, validate and serialise on top of `URLSearchParams`. Put the Context in the path, so that switching Context is a navigation and every query key carries it: `/c/$ctx/streams/$stream?seq=…&filter=…&tab=…`. One unverified risk is that TypeScript 7's Go-native compiler has not been tested against the Router's heavy type inference, so typecheck a route tree early in the build.

**Server state splits by feed shape.** TanStack Query 5.105 handles every request/response call. Its `refetchInterval` already pauses in hidden tabs, because `refetchIntervalInBackground` defaults to `false` and "focus" means `document.visibilityState` ([useQuery reference](https://tanstack.com/query/latest/docs/framework/react/reference/useQuery); [focus guide source](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/window-focus-refetching.md)). The WebSocket needs a plain-TypeScript client of about 50 lines that ref-counts topic subscriptions on the single socket and resubscribes on reconnect. Snapshot feeds (stream info, consumer lag, KV state, server stats) write into the Query cache with `setQueryData` under `staleTime: Infinity`. That follows TanStack Query maintainer TkDodo's advice: "if you update all your data via websockets anyways, consider setting a high `staleTime`" ([tkdodo.eu](https://tkdodo.eu/blog/using-web-sockets-with-react-query)). Append feeds (Live tail rows, chart rings) go into bounded stores read with `useSyncExternalStore` and flushed once per animation frame. Calling `setQueryData` per message would run structural sharing over the whole array on every frame. Skip `streamedQuery`: it is still exported only as `experimental_streamedQuery`, it accumulates every chunk by default, and its default refetch mode "erases all data" ([query-core source](https://github.com/TanStack/query/blob/main/packages/query-core/src/streamedQuery.ts)). Skip Zustand for live data too, since it adds nothing over `useSyncExternalStore` here. This client is the frontend half of the backend contract set earlier: one multiplexed socket per tab, metadata only, tails that drop the oldest frames and send gap markers, and metrics that collapse to the latest value per key. Unsubscribing high-rate feeds after a grace period when a tab is hidden matches the backend's ref-counted producers.

**Type the API with tygo, not an OpenAPI pipeline.** tygo v0.2.21 generates TypeScript from Go source. It keeps comments and `const` enums, maps `omitempty` to optional fields ([gzuidhof/tygo](https://github.com/gzuidhof/tygo)), and covers the WebSocket frame structs, which OpenAPI cannot describe. Run it from `go generate` and fail CI on a diff. The cost is that paths and methods live in a hand-written `api.ts` of about 30 functions. Huma v2.40, with its stdlib `humago` adapter, is the upgrade if a published, validated OpenAPI 3.1 contract is ever wanted ([danielgtaylor/huma](https://github.com/danielgtaylor/huma)). It means rewriting every handler into Huma's shape, though, and ADR-0001 promises only a domain API "to the browser". For tests, add Playwright's `page.routeWebSocket` (since v1.48, now v1.64.1) to mock the single socket ([Playwright WebSocketRoute](https://github.com/microsoft/playwright/blob/main/docs/src/api/class-websocketroute.md)). Reuse the tygo-generated frame types in those mocks so they cannot drift from Go. Use MSW 3's `ws` module for component-level mocks ([mswjs/msw](https://github.com/mswjs/msw/tree/main/src/ws)), and give each test a fresh `QueryClient` and a memory-history router.

## The message table outgrows every virtualiser at about 526,000 rows

ADR-0003 is right that very long streams need a scaled scrollbar. The numbers show the threshold is lower than "millions". **TanStack Virtual has no built-in scroll scaling.** Issue #616 ("Reach browser max height pixels") has been open since October 2023, with Chrome's cap given as 33,554,428 px and Firefox's as 33,554,400 px ([TanStack/virtual#616](https://github.com/TanStack/virtual/issues/616)). The community PR adding `maxScrollSize` was sent back on 27 October 2026. The maintainer's objections: it shrinks the items instead of compressing only the scroll offset, it should be opt-in, and "It also doesn't help Firefox, which caps at around 17.9M" ([TanStack/virtual#1172](https://github.com/TanStack/virtual/pull/1172)). AG Grid says the limit "is not published so can differ between different browsers as well as different browser versions" ([AG Grid docs source](https://github.com/ag-grid/ag-grid/blob/2058a4be8c9dd100906170bf7dcb6a839a570466/documentation/ag-grid-docs/src/content/docs/massive-row-count/index.mdoc)). With the prototype's 34 px rows, that is about **985,000 rows in Chrome and about 526,000 in Firefox**, if the maintainer's figure holds. Streams of that size are exactly the ones ADR-0003 was written for.

The prototype already does the right thing in principle. `messages.tsx` uses a fixed 4,000,000 px track, safely under every cap, with a pure ratio mapping from thumb position to row. That is AG Grid's "Stretching" approach, and AG Grid documents its flaw: with ten times the space needed, "the rows will appear to move x10 when scrolling… There is no way around this" ([AG Grid docs source](https://github.com/ag-grid/ag-grid/blob/2058a4be8c9dd100906170bf7dcb6a839a570466/documentation/ag-grid-docs/src/content/docs/massive-row-count/index.mdoc)). Glide Data Grid found a way around it. Large jumps (a scroll delta over 2,000 px, or reaching either edge) recalculate by percentage. Ordinary wheel and trackpad deltas "apply the delta directly to virtual position", which "preserves 1:1 pixel movement" ([glide-data-grid infinite-scroller.tsx](https://github.com/glideapps/glide-data-grid/blob/main/packages/core/src/internal/scrolling-data-grid/infinite-scroller.tsx)). **Keep the prototype's custom viewport and upgrade it to Glide's hybrid mapping** instead of waiting for TanStack's PR. Glide itself is not a candidate: its last npm release was February 2024, and it renders to canvas ([npm](https://www.npmjs.com/package/@glideapps/glide-data-grid)). Fixed-height rows need no measurement, so TanStack Virtual is optional here. It remains the right tool for the variable-height lists elsewhere: KV values, the JSON tree and the hex view.

The data feeding the table should follow the backend's consumer model, not the prototype's page arithmetic. Earlier backend research found that every ordered `Fetch()` deletes and recreates the server consumer, and that each consumer create is a Raft proposal in a cluster. That is why the backend keeps one ordered consumer per open view and creates a new one only on a jump or a filter change. The frontend equivalent is a **bidirectional `useInfiniteQuery` keyed by an anchor sequence**. Small scrolls call `fetchNextPage` or `fetchPreviousPage` on the same key, so the same consumer continues. A thumb drag past the jump threshold, or "Jump to seq", sets a new anchor, which re-keys the query and maps one-to-one onto a new backend consumer. Query's `maxPages` option keeps only a bounded set of pages "in both directions" ([TanStack Query infinite queries](https://github.com/TanStack/query/blob/main/docs/framework/react/guides/infinite-queries.md)). That implements ADR-0003's "distant pages evicted" without the prototype's hand-rolled LRU of 40 pages. Set `staleTime: Infinity`, because stored rows don't change once read. The thumb's size and position come from the stream's first and last sequence plus `NumPending`, so they stay approximate, as ADR-0003 accepts. Use TanStack Table v9 (9.0.0, August 2026) only for column definitions, sizing and visibility. It renames `useReactTable` to `useTable` and requires an explicit `features` option ([migration guide](https://github.com/TanStack/table/blob/main/docs/framework/react/guide/migrating.md)). Use no client row models, because filtering happens on the server. Two things are still unverified and must be tested before shipping. The first is keyboard paging (Page Down, Home, End) under scaling. The second is the real height cap in each engine. jsdom computes no layout, so this means Playwright runs on Chromium and Firefox, plus WebKit if a webview shell is adopted (section 5).

## uPlot, CodeMirror and two custom viewers handle the live and heavy data

### Charts: uPlot fits the data shape the backend already produces

One hour of 1 Hz samples is 3,600 points per series. The backend research already settled on fixed rings of 3,600 slots. That happens to be uPlot's own published streaming scenario. **uPlot 1.6.32 costs about 23.5 KB gzip tree-shaken**, against roughly 180 KB for a tree-shaken ECharts 6.1 line chart, 113 KB for Recharts 3.10, 57 KB for Chart.js 4.6 and 95 KB for Observable Plot. These numbers were measured for this research with esbuild and gzip; bundlephobia gives 21.9 KB for uPlot's whole entry ([bundlephobia uplot](https://bundlephobia.com/package/uplot@1.6.32)). The README says updating 3,600 points at 60 fps "uses 10% CPU and 12.3MB RAM", against 40% for Chart.js and 70% for ECharts ([uPlot README](https://github.com/leeoniya/uPlot#readme)). Two cautions apply. That is the author's own benchmark, dated 2023. And the same README reports 99% CPU on a Linux laptop when Chrome rasterises Canvas2D on the CPU ([uPlot README, rendering pipeline](https://github.com/leeoniya/uPlot#unclog-your-rendering-pipeline)). nats-ui updates at 1 Hz, not 60 fps, so even dozens of series cost little. Still, a WebKitGTK window with its DMA-BUF renderer disabled (section 5) is worth profiling once. uPlot has had no npm release in 19 months, but its master branch is active and is reworking tooltips, so **pin the version**. It has no documented theming or accessibility. Read colours from CSS variables with `getComputedStyle`, redraw on theme change, and pair each chart with a visually hidden summary and a "view as table" toggle. ECharts 6 is the fallback if built-in ARIA and runtime `setTheme` ever outweigh its size ([ECharts ARIA](https://echarts.apache.org/handbook/en/best-practices/aria/); [setTheme](https://echarts.apache.org/en/api.html#echartsInstance.setTheme)).

The prototype's chart data path needs replacing more than its rendering does. `useLiveSeries` in `kit.tsx` rebuilds its array with `[...p.slice(1), next]` every second. At 3,600 points that copies the whole series per tick, and it re-renders React each time. Use a columnar `Float64Array` ring outside React state, hand it to `u.setData()` from a subscription, and let React render the frame once. The KPI sparklines are about 120 px wide, so they can keep the prototype's zero-dependency SVG `Sparkline`. Feed it min/max downsampling to about two points per pixel and give it `role="img"` with an `aria-label` carrying the value and trend. Consumer-lag charts suit uPlot's stepped paths better than splines. Server-stat charts at one-second resolution depend on the backend polling `$SYS.REQ.SERVER.PING.STATSZ` every second, because the broadcast interval is fixed at 10 s ([nats-server events.go](https://github.com/nats-io/nats-server/blob/v2.15.2/server/events.go#L99-L107)).

### Editor: CodeMirror 6 at a tenth of Monaco's weight

**CodeMirror 6 builds a JSON editor with lint, folding, history and placeholder highlighting in about 115 KB gzip.** The same JSON-only Monaco 0.57 costs about 1.06 MB gzip of main-thread JS, plus CSS, a font and two workers of about 230 KB gzip together. Both were measured for this research. bundlephobia's 28 KB figure for Monaco measures only the entry stub ([bundlephobia monaco-editor](https://bundlephobia.com/package/monaco-editor@0.57.0)). Monaco's own FAQ answers "No" to whether it is supported in mobile browsers ([microsoft/monaco-editor](https://github.com/microsoft/monaco-editor)). CodeMirror says it "Works well with screen readers and keyboard-only users" ([codemirror.net](https://codemirror.net/)). One operational change to note: **CodeMirror's GitHub repos were archived on 15 April 2026** and moved to `code.haverbeke.berlin`. npm releases continue, with `@codemirror/view` 6.43.15 published 19 October 2026 ([GitHub API codemirror/dev](https://api.github.com/repos/codemirror/dev); [npm @codemirror/view](https://registry.npmjs.org/@codemirror/view/latest)). Issues and PRs now go there.

Placeholders need two pieces of custom code. Highlighting uses `MatchDecorator`, which "decorate[s] all matches" in the viewport ([CodeMirror decoration example](https://codemirror.net/examples/decoration/)). Use `Decoration.mark` rather than replacing widgets, so the token text stays editable. Use a regex that allows Go-template spacing and arguments (`{{ Random 10 100 }}`) ([natscli pub_command.go](https://github.com/nats-io/natscli/blob/7a43b35fa891a02196527373572e54658d94553e/cli/pub_command.go#L70-L87)). Validation cannot use `jsonParseLinter`, because `{"n": {{Count}}}` is invalid JSON until it is substituted. Instead, a custom linter swaps each placeholder for a stand-in of the same length (digits for `Count` and `Unix`, a quoted string otherwise), parses, and maps errors back one-to-one. It flags unknown names as errors, matching the prototype's refuse-to-send rule. Debounce it at 300 ms, and skip it above about 1 MB behind a "validate" button. The charts research could not tell from natscli's contradictory help text whether header values are templated. The earlier backend research settled it by reading the code: **natscli templates header values even with `--templates=false`**, evaluates each placeholder separately, never templates header names, and leaves a bad template unchanged instead of failing ([natscli headers.go](https://github.com/nats-io/natscli/blob/v0.5.1/internal/util/headers.go#L50-L66)). So the prototype's "copy as nats command" does reproduce header placeholders such as `Nats-Msg-Id: test-{{ID}}`. It is natscli's `--templates` flag description that misleads. One thing does need fixing: the prototype's `render()` in `publish.tsx` is a second, JavaScript implementation of natscli's template semantics, while the backend will vendor the Go original. Either serve the preview from the backend, or run both against shared golden fixtures, so the preview cannot drift from what is actually sent.

### Payload viewer: custom virtualised tree and hex, raw bytes on the wire

No React JSON viewer that was checked documents virtualisation. **A 4 MB JSON document measured for this research contains about 364,000 nodes.** react-json-view-lite 2.5.0 is excellent for small payloads: 2.6 KB gzip, the APG treeview keyboard pattern, dark styles ([AnyRoad/react-json-view-lite](https://github.com/AnyRoad/react-json-view-lite)). But it puts every expanded node in the DOM, so "expand all" on a large array would create hundreds of thousands of elements. Build one custom flattened tree on `@tanstack/react-virtual`, with `role="tree"` and `treeitem` rows carrying `aria-level` and `aria-expanded`. Cap a single opened array at 1,000 children per page, which mirrors how the message table pages. The benchmark also showed where the cost really lies. In V8 on a desktop CPU, `JSON.parse` of 4 MB took about 19 ms, but `structuredClone` of the parsed graph took about 45 ms. Parsed objects cannot be transferred zero-copy, only `ArrayBuffer`s can ([MDN Transferable objects](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Transferable_objects)). So parse on the main thread for desktop-sized cases. If low-end devices jank, keep the tree inside a worker and ask it for `rows(start, count)`, rather than parsing in a worker and posting the tree back. These were Node/V8 measurements, not browser ones. Firefox, Safari and phones were not measured.

ADR-0003's progressive load interacts with this in a way the ADR does not spell out. **The first 64 KB of a 4 MB JSON is almost always truncated, invalid JSON**, so show it as highlighted text in a read-only CodeMirror view, labelled with the loaded and total size. Switch to the tree when the full bytes arrive. Decode the chunk with `TextDecoder.decode(chunk, {stream: true})` so a split multi-byte character does not throw ([MDN TextDecoder.decode](https://developer.mozilla.org/en-US/docs/Web/API/TextDecoder/decode)). The hex view should also be custom. The only React option, `react-hex-editor`, was last released in 2020 ([npm](https://registry.npmjs.org/react-hex-editor)). The prototype's `hexDump` builds the whole dump as one string, about 18 MB of UTF-16 for a 4 MB payload. A virtualised view formats 16-byte rows from a `Uint8Array` on demand, and formatting all of a 64 KB chunk took 1.3 ms in the local benchmark.

The split between browser and backend follows from what each side already holds. The Go client has headers already parsed from the ADR-4 wire format, which is multi-valued and case-preserving ([ADR-4](https://github.com/nats-io/nats-architecture-and-design/blob/main/adr/ADR-4.md)). So the backend sends them as JSON, and nobody writes a TypeScript header parser. Payloads travel as raw bytes through the HTTP Range endpoint the backend research proposed (`http.ServeContent` over a `bytes.Reader`) ([net/http ServeContent](https://pkg.go.dev/net/http#ServeContent)), never as base64 inside JSON, which adds 33% ([RFC 4648 §4](https://www.rfc-editor.org/rfc/rfc4648#section-4)). The browser detects the payload kind from bytes it fetches anyway. It checks a `Content-Type` header hint first, then a first-byte sniff with `TextDecoder({fatal: true})` (0.7 ms on 4 MB locally), then the user's Auto/Text/Hex override. One hard rule follows from the desktop research: **never render NATS payloads in an iframe**. Wails v3 still lets same-origin child frames on Linux reach its native bridge ([Wails v3.0.0 release](https://github.com/wailsapp/wails/releases/tag/v3.0.0)), and plain text rendering is safer in every shell anyway.

## The prototype's most-used text colour fails WCAG 2.2 AA

### Contrast audit: one failing tier, one failing chip, everything else passes

The prototype palette was audited with the WCAG 2.x relative-luminance formula, unrounded, so 4.499:1 fails ([W3C SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)). Status tints were composited over each surface before measuring. The surfaces step evenly in OKLCH lightness, from 15.5% (bg) to 18.7% (panel) to 21.8% (raised), which makes a clean elevation ramp. The text tiers are uneven:

| Text token | on bg `#0b0c0f` | on panel `#111318` | on raised `#171a21` | AA (4.5:1) |
|---|---|---|---|---|
| fg `#e7e9ee` | 16.10 | 15.30 | 14.33 | pass |
| muted `#8a92a3` | 6.26 | 5.95 | 5.57 | pass |
| **faint `#5b6271`** | **3.19** | **3.04** | **2.84** | **fail** |
| accent `#2dd4bf` | 10.51 | 9.98 | 9.35 | pass |
| ok / warn / bad / info | 11.22 / 11.72 / 7.07 / 7.69 | 10.66 / 11.13 / 6.72 / 7.31 | 9.99 / 10.43 / 6.29 / 6.85 | pass |

**`faint` fails on every surface, and it is the most-used text colour in the prototype**: 29 uses against 23 for `muted` and 20 for `fg`, often at 10–11 px. Three more pairs fail. Faint on the active-nav tint is 2.56:1. Faint on the `bg-black/20` code chip is 3.13:1, and that chip shows the CLI equivalents and the typed-confirm command preview, which are core to nats-ui's "copy as nats command" identity. White on `bad` would be 2.77:1, so destructive buttons need dark text (7.59:1). The status badges all pass on their own 10% tints, from 5.49:1 (bad on raised) to 9.95:1. The amber Read-only badge is robust at 8.5–10:1. The fix keeps faint's hue and chroma and raises only its OKLCH lightness:

| faint candidate | hex | bg | panel | raised |
|---|---|---|---|---|
| L 0.496 (today) | `#5b6271` | 3.19 | 3.04 | 2.84 |
| L 0.60 | `#798090` | 4.95 | 4.70 | 4.41 |
| **L 0.615 (recommended)** | **`#7d8595`** | **5.26** | **5.00** | **4.68** |

To keep the hierarchy's steps, raise muted to `oklch(72% 0.027 265)` = `#9ca5b6`, which measures 7.49:1 on panel. Panel then reads fg 15.3, muted 7.5, faint 5.0, and every tier passes on every surface. Keep the old faint only as a renamed `--fg-disabled` token for disabled text (exempt under SC 1.4.3), separator glyphs and decorative JSON punctuation. Borders sit far below 3:1 (`line` is 1.24:1 on panel). That is fine for decoration, but SC 1.4.11 requires 3:1 wherever a boundary is the only cue that a control exists ([W3C SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). A new `--input` border of `#626978` (3.37:1 on panel) covers inputs and selects. APCA is useful as a design aid. It flags that `muted` at 11–13 px (Lc about 43) feels weak even at 6:1. But it is not a standard: as of the April 2026 Editor's Draft, "The contrast algorithm used in WCAG 3 is yet to be determined" ([Adrian Roselli](https://adrianroselli.com/2026/04/wcag3-contrast-as-of-april-2026.html); [WCAG 3 Editor's Draft](https://w3c.github.io/wcag3/guidelines/#dfn-contrast-ratio-test)). Ship to WCAG 2.2 AA. No light palette was computed in this research, so a light theme still needs values and its own audit.

### Tokens: three layers in OKLCH, mapped onto shadcn's names

Tailwind v4 requires `@theme` variables to be "defined top-level and not nested under other selectors or media queries", and `@theme inline` exists for "theme variables that reference other variables" ([Tailwind theme variables](https://tailwindcss.com/docs/theme)). That dictates three layers. Raw OKLCH ramps go in plain `:root` variables. Semantic tokens go under `:root, [data-theme="dark"]`, overridden by `[data-theme="light"]` and later `[data-contrast="more"]`. A single `@theme inline` block maps the semantic tokens onto utilities, with `--color-*: initial` so stray Tailwind colours such as `teal-400` cannot creep back in. This is shadcn's own pattern, with tokens in `oklch()` and dark mode done by overriding the same names ([shadcn theming](https://ui.shadcn.com/docs/theming)). The prototype's `index.css` puts literal hex values directly in `@theme`, which is the one place they cannot be overridden per theme. **The prototype's names also collide with shadcn's.** Its `accent` is the brand teal, but in shadcn `accent` is the hover and selected surface. Its `muted` is a text colour, but shadcn's `muted` is a surface and `muted-foreground` is the text. Map the teal to `primary` and `ring`, and the secondary text to `muted-foreground`. Add `success`, `warning`, `info`, a tertiary text token and `readonly` (an alias of warning) as extras. Then replace the dark-only literals: `bg-white/5`, `bg-black/30`, `text-black` and the `rgb()` in the `flash` keyframes. After that, a light theme is one selector block of about 30 values with no component edits. Use a three-state `data-theme` (system, dark, light), with the inline head script Tailwind recommends to avoid a flash of the wrong theme ([Tailwind dark mode](https://tailwindcss.com/docs/dark-mode)). Always set `color-scheme` on `:root`, because WebKitGTK otherwise leaks a light GTK theme into native controls such as `<select>` popups ([WebKit bug 197947](https://bugs.webkit.org/show_bug.cgi?id=197947)). The reference systems converge on this model: Radix's 12 steps with fixed roles, Primer's base/functional/component tiers, Geist's background/border/text bands, and Linear's three-variable LCH generator ([Radix scale](https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale); [Primer](https://primer.style/foundations/color/overview); [Geist](https://vercel.com/geist/colors); [Linear](https://linear.app/now/how-we-redesigned-the-linear-ui)). On a Radix-style scale, the fixed faint and muted land at steps 10–11, so the light theme has a ready template.

### Fonts: Inter Variable and Geist Mono, bundled into the binary

**The prototype loads no font files.** Its `--font-sans: "Inter", "Geist", …` does not match Fontsource's family names (`'Inter Variable'`, `'Geist Mono Variable'`), so today it renders with whatever happens to be installed. All five candidate families are SIL OFL 1.1, so they can be bundled freely ([rsms.me/inter](https://rsms.me/inter/); [vercel/geist-font](https://github.com/vercel/geist-font); [JetBrains Mono](https://github.com/JetBrains/JetBrainsMono); [IBM Plex](https://github.com/IBM/plex)). Use **Inter Variable** for the UI. It has `tnum`, a slashed `zero`, `ss02` disambiguation for Il1 and O0, and an optical-size axis that gives Linear-style Display headings without a second family. For mono, use **Geist Mono**, which has no `calt` or `liga` ligatures and a marked zero by default. JetBrains Mono, the prototype's current first choice, ships ligatures on by default. With it, every subject and ID cell needs `font-variant-ligatures: none`, because NATS subjects are built from `.`, `*` and `>`. Inspecting the font files showed that **Inter's and Geist's default digits are proportional**, so tables need `font-variant-numeric: tabular-nums` globally rather than the prototype's opt-in `.tabular` class. Fontsource's Latin subsets are 22–71 KB per family, but they strip Inter's `zero`, `ss` and `cv` features. If you want the slashed zero, ship the official 343 KB `InterVariable.woff2`, or subset it yourself with those features kept. Vite emits hashed woff2 assets that `//go:embed` bundles into the binary ([pkg.go.dev/embed](https://pkg.go.dev/embed)), so fonts work offline with no CDN. Add a `preload` link for the sans.

### Omarchy theme following belongs in Go, and every shell benefits

`prefers-color-scheme` carries only dark or light, and Linux webviews are unreliable at even that ([WebKit bug 197947](https://bugs.webkit.org/show_bug.cgi?id=197947)). Omarchy exposes far more. On the installed Omarchy 4.5.0rc2, `~/.local/state/omarchy/current/theme/colors.toml` holds a `mode` key plus about 30 named colours. `theme.generation` is rewritten on every theme switch. User templates in `~/.config/omarchy/themed/*.tpl` and hooks in `~/.config/omarchy/hooks/theme-set.d/` are official extension points ([basecamp/omarchy](https://github.com/basecamp/omarchy)). Older guides cite `~/.config/omarchy/current/`, but that path does not exist on 4.5. Omarchy's own `omarchy-theme-set-gnome` turns `mode` into the gsettings `color-scheme`. The freedesktop portal adds `contrast` and `reduced-motion`, with a change signal ([xdg-desktop-portal Settings](https://flatpak.github.io/xdg-desktop-portal/docs/doc-org.freedesktop.portal.Settings.html)). The design that fits nats-ui is an **opt-in "Follow Omarchy" mode run by the Go backend**:

1. Watch `theme.generation` with fsnotify, and re-read `colors.toml` when it changes.
2. Map `background`, `lighter_background`, `foreground`, `accent` and `selection` onto the semantic tokens, and `mode` onto `data-theme`.
3. Raise the OKLCH lightness of any text token until it reaches 4.5:1 on its surface.
4. Push the token set as a `theme` topic on the existing WebSocket. The frontend writes the values onto `:root`, and the `@theme inline` mapping does the rest.

The re-validation step matters. Theme authors' "muted" colours are often far below AA; Tokyo Night's `#414868` on `#1a1b26` looks it, though it was not measured. Keep the status semantics recognisable, above all the amber Read-only cue, unless the theme's own red, yellow and green pass. The alternative is a `nats-ui.css.tpl` that the user drops into `themed/`. It is closer to how Omarchy's built-in integrations work, but it needs a manual install. Omarchy's first-party apps (Hype, Monologue, Omacut) read the same file natively. The key point is that **a Go-side theme feed gives live Omarchy theming to the browser tab, the `--app` window and any webview alike**. Theme following is no reason to go native. On macOS and Windows the feature falls back to `prefers-color-scheme`.

### Accessibility: four gaps to close before the first release

A grep of the prototype finds no `aria-live`, no `role="status"` and no `role="grid"`. It also finds `outline-none` on the palette, typed-confirm and select inputs, replaced only by a 1 px `bad/60` border (3.12:1) that falls below the 2 px area guideline. **First, focus:** replace `outline-none` everywhere with a 2 px solid teal `focus-visible` outline offset outside the element. It measures about 10:1 on panel and passes both SC 1.4.11 and the AAA Focus Appearance guidance ([W3C SC 2.4.13](https://www.w3.org/WAI/WCAG22/Understanding/focus-appearance.html)). Inside teal-tinted selected rows, use a two-tone ring. **Second, live data:** SC 2.2.2 is Level A, has no five-second exception for auto-updating content, and requires a way "to pause, stop, or hide it or to control the frequency of the update". For real-time data, resuming should jump to current values ([W3C SC 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)). A global "Pause live updates" control satisfies that, and it maps cleanly onto unsubscribing socket topics. **Third, announcements:** never put per-second counters in a live region. Keep one visually hidden polite `role="status"` region, present from the first render, and announce coalesced threshold crossings such as "Consumer orders-worker stalled". `assertive` is for critical notices only, and `role="alert"` should not be combined with `aria-live` ([MDN live regions](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Guides/Live_regions)). No source gives a throttle interval, so that is a design choice. **Fourth, motion and targets:** wrap the `.flash` highlight in `motion-safe:` with a static fallback marker. Size clickable badges (such as the Read-only toggle, at `py-0.5` and 10–11 px) to the 24×24 px minimum of SC 2.5.8, or space them out ([W3C SC 2.5.8](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). Most nats-ui lists are read-and-drill-down, so use semantic `<table>`s with a sortable `<button>` per header and one link per row. Use the APG grid pattern, with its single tab stop and author-managed focus, only for genuinely interactive tables with several per-row actions ([WAI-ARIA APG grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/)). Make density a token (`--row-h` of about 28/32/36 px, plus cell padding) instead of the hard-coded `py-1.5`, and keep controls at 24 px or more.

## A Chromium app window beats a webview on your own machine

Should nats-ui ship as a desktop app? Yes, in the sense that it should open as its own chromeless, separately tiled, launcher-listed window. No, in the sense that this does not require a second toolchain yet. The comparison turns on one structural fact. **Every option that loads the UI from the Go server's own `http://127.0.0.1:PORT` origin keeps ADR-0001's Launch token, Host check and Origin check unchanged**: a Chromium `--app` window, a PWA, Wails over loopback, Tauri with an external URL, Electron's `loadURL` and Qt WebEngine. So the choice is about distribution, native affordances and rendering engine, not about the UI or its security.

| | Chromium `--app` + `.desktop` + PWA manifest | Wails v3, shell over loopback | Tauri v2 + Go sidecar | Electron 45 + Go child | Qt WebEngine shell | Native QML rewrite |
|---|---|---|---|---|---|---|
| Extra toolchain | None | None (Go), but cgo on Linux and macOS | Rust | Node | C++/Qt | C++/QML, and a second UI |
| Added size | ~0 (installed browser) | Tens of MB; NUI ships 75–78 MiB on Wails v2 | Small deb/rpm, or 70+ MB AppImage | ~85 MB+ (third-party figure) | ~283 MiB qt6-webengine on Arch | ~0.3–0.7 MiB on Arch (system Qt) |
| ADR-0001 single binary and `go install` | Kept | Desktop build becomes a second artifact | Lost | Lost | Lost | Lost |
| Linux engine | Chromium, native Wayland | WebKitGTK 6.0 | WebKitGTK | Chromium | Chromium | Qt Quick |
| Tray, menus, dialogs, installers, updater | None | All | All (updater: AppImage only on Linux) | All | Build it yourself | Native |
| Token handover | URL on the browser's argv | In-process, never printed | Sidecar stdout | Child stdout | Child stdout | Needs a redesign |

**The browser path is the right first desktop app.** Loopback is a secure context ([MDN Secure contexts](https://developer.mozilla.org/en-US/docs/Web/Security/Secure_Contexts)). PWAs can be installed from `localhost` or `127.0.0.1` "with or without a port number" ([MDN installable PWAs](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)). Chrome dropped the service-worker requirement for menu install in Chrome 112 on desktop ([Chrome blog](https://developer.chrome.com/blog/update-install-criteria)). Omarchy's own web-app convention is just a `.desktop` file. `omarchy-webapp-install` accepts a custom `Exec`, and `omarchy-launch-webapp` runs the default Chromium-family browser with `--app=` and a window class that strips the port, so the class stays stable ([basecamp/omarchy](https://github.com/basecamp/omarchy)). The one design problem is the Launch token. A window opened from the launcher cannot read a token printed to a terminal, so **the binary itself must be the launcher**. `nats-ui open` starts the server, or attaches to one that is running, and opens `--app=http://127.0.0.1:PORT/launch?token=…`. The process-lifetime token and the 303 redirect with `no-referrer` from the backend research do the rest. A `nats-ui install-desktop` command can write the Omarchy or XDG entry with that `Exec`. Be precise about one weakness: the token sits on the browser's argv for a moment. That is the same exposure the backend research flagged for `cli/browser`, and Jupyter's redirect-file option exists to avoid it on shared machines ([jupyter_server serverapp.py](https://github.com/jupyter-server/jupyter_server/blob/main/jupyter_server/serverapp.py)). A PWA adds two constraints. The origin includes the port, so install identity and cookies need a **stable default port**. And an installed PWA opens `start_url` without a token, so it only works while a session is still valid. Adding token-free re-authentication would weaken the model, so treat the manifest as a cheap extra, not the primary path. The browser path's limits are real but small for a localhost console: no tray or native menus, a dependency on a Chromium-family browser (Firefox's equivalent was not researched), and the session cookie living in the user's normal browser profile.

**If you want a real app window, Wails v3 in shape A is the upgrade, but not yet.** v3.0.0 went stable on 26 October 2026, "nearly four years" after the first alpha. It requires Go 1.26+, ships weekly minor releases, and its own notes say "Pin an exact version in production builds" ([v3.0.0 release](https://github.com/wailsapp/wails/releases/tag/v3.0.0)). Its in-process asset server cannot host nats-ui as it stands. It **returns 501 for WebSocket upgrades** ([assetserver.go](https://github.com/wailsapp/wails/blob/v3.0.0/v3/internal/assetserver/assetserver.go#L84-L88)). Cookies do not work on its custom scheme, an upstream webview limitation that "Version 3 doesn't change" ([Wails #3908](https://github.com/wailsapp/wails/issues/3908)). And on Windows it buffers whole responses, so "a streaming response cannot work on Windows today" ([responsewriter_windows.go](https://github.com/wailsapp/wails/blob/v3.0.0/v3/internal/assetserver/webview/responsewriter_windows.go#L33-L42)). Shape A sidesteps all three. The desktop entry point starts nats-ui's normal server on `127.0.0.1:0` and sets the window's `URL` to the `/launch?token=` address, a documented option for loading "external URL instead of embedded assets" ([Wails window options](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/features/windows/options.md)). The token then never touches stdout or any argv, which is better than the browser path. Wails adds a tray, menus, native dialogs, single instance and a signature-checking updater, and it builds AUR, deb, rpm, AppImage, NSIS, MSIX and DMG packages ([updater guide](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/guides/updater.md); [Linux build guide](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/guides/build/linux.md)). The costs: **cgo on Linux and macOS but not Windows** ([cross-platform guide](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/guides/build/cross-platform.md)), and dynamic links to GTK4 and WebKitGTK 6.0, about 139 MiB installed on Arch ([Arch webkitgtk-6.0](https://archlinux.org/packages/extra/x86_64/webkitgtk-6.0/)). The desktop binary therefore cannot run headless or be built by `go install`. Keep the default build `CGO_ENABLED=0` and put Wails behind a `desktop` build tag, so the headless binary's dependency graph is unchanged. Build Linux and macOS desktop artifacts on native CI runners. Shape B, fully in-process with Wails Streams replacing `/ws`, removes the TCP port ("no bound TCP port, no origin check, no token") ([Streams migration guide](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/guides/streams-from-websockets.md)). But it forks the live transport and the auth middleware, so leave it for later. NUI, the closest NATS GUI, is the cautionary example. On Wails v2, its desktop build calls a Fiber server on `:31311` that binds all interfaces, with CORS `*` and no token ([nui server.go](https://github.com/nats-nui/nui/blob/71d1487c47cc99f3fc379ddb8236cb3463e21d0a/internal/nui/server.go#L42-L52)). Shape A is safe only because nats-ui keeps every check.

The rendering engine is what tips the timing for you. Your machine runs Hyprland 0.56.2 on an **NVIDIA RTX 2080**. Wails' own Linux guide documents "a blank or white window" from a WebKitGTK DMA-BUF bug on NVIDIA drivers 377–580+. Wails sets `WEBKIT_DISABLE_DMABUF_RENDERER=1` automatically when it detects NVIDIA rendering ([Wails Linux guide](https://github.com/wailsapp/wails/blob/v3.0.0/docs/mpress/content/guides/build/linux.md)). Tauri's guide adds `__NV_DISABLE_EXPLICIT_SYNC=1` for the Wayland "Error 71" crash, and warns against unconditional overrides ([Tauri Linux graphics](https://v2.tauri.app/develop/debug/linux-graphics/)). Wails v3 also has open Linux issues that touch you directly. On Hyprland, the cursor warps to an attached tray window ([#5839](https://github.com/wailsapp/wails/issues/5839)). Closing a window leaks its WebKitWebProcess, "~50 MB leaked per window" ([#6505](https://github.com/wailsapp/wails/issues/6505)). Tray `openMenu()` is missing on Linux ([#6327](https://github.com/wailsapp/wails/issues/6327)). Chromium, by contrast, is already Omarchy's web-app runtime and runs natively on Wayland. Adopting Wails would also widen the frontend test matrix. Playwright's WebKit engine would join Chromium and Firefox, the scaled table's height cap in WebKit would need measuring, and Ctrl/Cmd+K would need one owner, either a menu accelerator or the page, since Wails turns off WebView2's browser accelerator keys on Windows ([webview_window_windows.go](https://github.com/wailsapp/wails/blob/v3.0.0/v3/pkg/application/webview_window_windows.go#L2742)). Revisit Wails once v3 has a few months of hotfixes and those Linux issues are closed. Avoid `webview/webview_go` outright. Its last commit was in August 2024, and it hard-codes `webkit2gtk-4.0`, which Arch no longer ships ([webview.go](https://github.com/webview/webview_go/blob/6173450d4d/webview.go#L4-L15)).

The non-Go shells rank behind Wails for a Go project. **Tauri v2** (2.12.5, 21 October 2026) works cleanly as a thin shell. The Go binary runs as an `externalBin` sidecar named per target triple, the window loads the Go origin as a remote URL, and that page gets no Tauri IPC by default, which is the safest setting ([Tauri sidecar](https://v2.tauri.app/develop/sidecar/); [Tauri capabilities](https://v2.tauri.app/security/capabilities/)). It adds Rust, a sidecar per triple, and a lifecycle the docs don't cover (killing the child on exit). On Linux its updater documents only AppImages ([Tauri updater](https://v2.tauri.app/plugin/updater/)), and the AppImage grows "to 70+ MB" ([Tauri AppImage](https://v2.tauri.app/distribute/appimage/)). It renders on the same WebKitGTK as Wails, so it offers no engine advantage. **Electron 45** has secure defaults and native Wayland since 38.2 ([Electron security](https://www.electronjs.org/docs/latest/tutorial/security); [Electron Wayland](https://www.electronjs.org/blog/tech-talk-wayland)). But it bundles a whole Chromium to show a page your installed Chromium already renders, and it approves all permission requests unless a handler is set. A **Qt WebEngine shell** costs about 283 MiB, cannot be built statically, and is not Mac App Store compatible ([Qt WebEngine platform notes](https://doc-snapshots.qt.io/qtwebengine/qtwebengine-platform-notes.html)). On Omarchy it gains nothing over `--app`. A **native QML app** in the style of Hype, Monologue and Omacut would be a perfect Omarchy citizen at under 1 MiB on system Qt ([omacom/hype](https://github.com/omacom/hype)). But it means rewriting every screen, and it ends the "web console" the glossary describes. That is a product decision, not a packaging one.

|---|---|---|
| ADR-0001: browser never connects to NATS; domain API plus one WebSocket | **Confirms** | Every desktop option worth considering loads the Go origin, so the domain API stays the only client surface. tygo types both the REST DTOs and the WebSocket frames from Go. |
| ADR-0001: single binary is the only way the app is distributed | **Holds for the browser path, challenged by any true desktop build** | `--app`, `.desktop` and a PWA keep one binary and `go install`. In shape A the token is handed to the window in-process. Shape B would make them moot, but would split the middleware by transport. NUI shows the cost of dropping them. |
| ADR-0003: metadata-only rows, pages of 100, distant pages evicted | **Confirms, refines** | Implement eviction as `useInfiniteQuery` keyed by anchor sequence with `maxPages`, so query keys map onto the backend's one-consumer-per-view rule. |
| ADR-0003: scaled scrollbar because browsers cap element height | **Confirms, sharpens** | No virtualiser solves it (TanStack #616 open, #1172 sent back). | ADR-0003: Live tail keeps rows when payloads are dropped | **Confirms** | The frontend ring with gap markers mirrors it. SC 2.2.2 adds a required pause control that resumes to current values. |
| Glossary: "A web console" | **Confirms** | Every recommended path keeps the React UI. Only a QML rewrite would end it. |
| Glossary: Launch token "the app prints at startup" | **Refines** | In launcher and desktop modes the token is never printed: it travels in the launch URL (`--app`, briefly on argv) or in-process (Wails). |
| Glossary: Placeholder uses natscli's template names | **Confirms, refines** | natscli templates header values unconditionally, so "copy as nats command" reproduces header placeholders. The prototype's JS `render()` duplicates the Go semantics and needs shared golden tests or a backend preview. |

## Conclusion

The research separates two questions that looked joined. Everything hard about nats-ui's frontend is solved in the page and the Go backend, whatever shell hosts it: scrolling a million-row stream, rendering a 4 MB payload without jank, meeting contrast on dense dark surfaces, and following Omarchy's live theme. Every serious shell loads the same `127.0.0.1` origin. So the desktop question shrinks to distribution and native affordances, and it can be answered later and cheaply. On your own hardware, the native-looking option (a WebKitGTK webview) is actually the less reliable renderer, and the "just a browser" option is the one Omarchy itself uses for web apps. Theme following works the same way: built in Go, it reaches every shell at once.

The most consequential frontend fixes are small and come first. One lightness change to `faint` clears the only failing text tier. Moving tokens out of `@theme` makes a light theme and Omarchy following possible at all. Loading real font files makes the typography deterministic. Upgrading the scaled table to a hybrid mapping, and keying its queries by anchor sequence, ties the UI's scroll behaviour directly to the backend's consumer budget. Three items change recorded text, not just code: the single-binary clause of ADR-0001 if Wails ships, the Launch token's "prints at startup", and the Placeholder's header semantics. Settle those alongside the backend report's open decisions, since both reports converge on the same Launch-token and templating definitions.
